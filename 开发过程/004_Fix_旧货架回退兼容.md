# 旧货架回退兼容

## 背景

YOS `0.1.14` 的发布手册要求切换前用当前 `verify-public-shelf.mjs`
全量自审旧货架，并在回退后再次以签字模式核验。第一轮实现依据 Git
时间线，错误假设生产旧货架“已有 `buildId` 和能力目录，只缺
`publicationMode`”。小A从生产只读复制出的真实 0.1.13 货架证明：
`buildId`、`publicationMode`、`capabilities.json` 三项都不存在。因此第一轮
兼容条件永远无法命中，回退签字也会被不存在的 `buildId` 卡住。

仓内发布记录保留了生产旧货架证据：874 个实际文件、873 个登记文件，
`index.json` SHA-256 为
`ea64d43821e814c12a7e83e90269dfc7b67e9ab6b1f8ef5d7dd838095b04f9c1`。
当前开发机没有货架机 SSH 权限，未读取或修改生产备份；真实三缺失形状来自
小A的只读真机复验。仓内固定摘要来自 0.1.14 发布切换前记录，不冒充本机
生产原件实测。

## 关键决策

增加显式 `--allow-legacy-0.1.13`，但不把“字段缺失”全局解释为
production。兼容只在以下条件全部满足时成立：

1. `buildId`、`publicationMode`、`capabilities.json` 必须同时缺席，显式
   `test-only` 仍拒绝。
2. 最新 Core 标签必须是 `v0.1.13`。
3. `index.json` SHA-256 必须等于切换前留档的
   `ea64d43821e814c12a7e83e90269dfc7b67e9ab6b1f8ef5d7dd838095b04f9c1`。
4. 必须执行 `--full`，且只能用于本地备份自审或带兼容凭据的 `--signoff`。
5. `index.json` 的逐文件哈希、预期摘要和核心版本校验继续执行；旧货架没有
   provider 目录，因此不伪造 provider 校验结果。

0.1.13 没有 provider 目录，因此兼容签字只要求核心版本和完整 index 摘要，
不要求不存在的 `buildId`/provider。发布手册只在 `OLD=0.1.13` 时加入该参数；
更新版本和正常发布签字仍要求三项现代凭据。

## 否掉的方案

- **缺现代字段一律按 production**：会让新货架删除字段后也通过，
  等于拆掉现有门禁。
- **手工修改旧货架 `index.json` 补字段**：会改变已发布备份的清单哈希，破坏
  回退证据，且属于不必要的生产修改。
- **跳过旧货架自审/回退签字**：会让“可回退”退化成未验证的文件复制。

## 测试结果

- 默认路径对三项缺失的 0.1.13 继续 fail-closed。
- 纯函数验证真实三缺失结构；完整 CLI 正向链待小A用生产只读副本复验。
- 新版本缺字段、显式 `test-only`、出现 `buildId` 或能力目录全部拒绝。
- 兼容签字不再要求旧货架不存在的 `buildId`，但必须命中固定 index 摘要。
- 非本地且非签字路径使用兼容开关，在读取货架前拒绝。
- 通过软链接执行校验器时仍会进入主程序；损坏货架返回非零，不再静默成功。
- 现代货架存在 `capabilities.json` 但未在 `index.json` 登记时必须拒绝。
- 手册两处兼容参数均被文档测试锁定为只对 `OLD=0.1.13` 生效。
- 定向测试：69/69 通过；五次撤销或旧版反证均精确报红。
- 完整门禁：Jest 432/432、Node 1544/1544、6 个依赖根 0 漏洞。
- 正式包：477 项，内容摘要
  `5f4907397e4a01a2ded9f600388e29f74d543b29af0d99ac3651f015776723d6`；
  同轮双构建压缩包 SHA-256
  `34bbfeea0337960e394946262feb6198322cc062082d6e64c6cd0d11ece24858`。
- `npm run verify`：PASS。
