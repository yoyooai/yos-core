# Feature: 自升级事务安全

## 背景

原自升级有两个结构问题：

1. `npm pack` 会触发全仓发布门禁，但客户下载的源码归档没有 `.git` 和开发依赖，因此升级必然在全局安装前失败。
2. 新核心安装后的步骤 5–12 失败时不回滚，可能留下新旧版本混合且服务停止的机器。

## 关键决策

### 1. 分开发布门禁和客户端候选包

- `npm run release:pack` 是正式制品入口：先运行完整 `verify`，然后打包。
- `prepublishOnly` 防止直接 `npm publish` 绕过门禁。
- 普通 `npm pack` 不再运行全仓门禁，仅用于客户端事务内生成已下载候选包。

否掉的方案：在无 `.git` 时让 `verify` 自动降级。这会让正式发布门禁在需要它时静默失效。

### 2. 在停服务前做真实可执行预检

- 检查临时目录、至少 512 MiB 可用空间和 npm 可用性。
- 把每个带生产依赖的 Core Skill 清单复制到隔离目录，真实执行 `npm install --omit=dev`。
- 预先生成新核心候选包。任一操作失败时，备份和停服务步骤都不会开始。

否掉的方案：硬编码检查 `make/gcc/python3`。原生依赖可能有适配当前平台的预编译包；真实安装预演比工具名清单更准确，也能提前发现 Registry、ABI 和安装脚本问题。

### 3. 核心包、Skill 和服务统一回滚

- 步骤 1 同时打包当前核心，备份目录权限为 `0700`，回滚状态为 `0600`。
- 步骤 4–12 失败时，依次恢复旧核心、Skill、Skill 依赖、PM2 配置和原先在线服务，最后验证服务确实 online。
- 自动回滚不完整时，返回 `machineState=recovery_required`、备份路径和 `yos upgrade --self --recover <backup>`。
- 步骤 13 只在服务已验证可用后提交基线；它失败时保持新版运行，明确告警并保留备份。

### 4. 成功清理与更新说明降级

- 备份清理移入核心 finalizer，所以人读与 `--json` 成功路径行为一致。
- 更新说明只从已下载包读取；缺失或不可读时用固定文案告警，不再访问第三方仓库。

## 升级路径网络依赖

| 阶段 | 端点 / 命令 | 必要性 | 失败行为 |
|---|---|---|---|
| 检查版本 | GitHub tags API；分支模式读取发布源 `package.json` | 必需 | 升级不开始，服务不停 |
| 下载候选 | 配置的 YOS GitHub 发布源 archive；私有仓失败时可用 GitHub API | 必需 | 升级不开始，服务不停 |
| 预装及恢复 Skill 依赖 | npm Registry | 必需 | 预检阶段拒绝；若回滚恢复依赖失败则显式标记恢复不完整 |
| 更新说明 | 无额外请求，仅读已下载的 `CHANGELOG.md` | 可选 | 固定告警后继续 |

## 验证记录

- 无 `.git` 且无 `node_modules` 的源码副本：`npm pack --ignore-scripts` 成功。
- 真实预检：5 个带生产依赖的 Core Skill 安装预演成功，候选 tgz 生成成功。
- 定向测试：发布门禁、预检、回滚、步骤 13 告警、恢复入口、JSON 备份清理、可选更新说明均通过。
- 全量门禁数字在完成时回填；真实隔离升级与故障回滚由独立验收人执行。

## 影响范围

仅影响 YOS Core 正式打包和 `yos upgrade --self`。不改组件升级、运行时、消息、记忆、渠道和数据库契约。
