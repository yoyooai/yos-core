# 组件同版本自愈与能力标题一致性

## 背景

飞书组件的版本号已经是最新时，`yos upgrade feishu` 原先直接返回
`up to date`。如果 `lark-cli` 的子技能下载曾经中断，缺失文件不会被再次
检查，命令会把一个不完整的安装误报为健康。

公共能力标题也存在两个来源：本地目录读取组件声明，货架构建按 provider
遍历顺序取第一个标题。同一个 `communication.message` 因而可能显示为
`Message routing` 或 `飞书消息`。

## 决策

- 生命周期新增可选的 `repair` 钩子。只有显式声明该钩子的组件会在
  “版本相同”时运行完整性检查；旧组件保持原行为。
- 不复用 `post-upgrade`。升级迁移可能有副作用，重复执行不能被当作修复。
- repair 失败必须阻止“已是最新”的成功结论，并返回稳定错误码、阶段和
  修复建议。
- 公共能力标题由 Core 的同一解析器决定；provider 名称保留在 provider
  记录中，不再反向覆盖公共标题。
- 未知的新能力 ID 仍可按 ID 生成稳定标题，因此新增组件不需要先升级 Core。

## 未采用方案

本轮不把 27 个飞书子技能镜像进 YOS 货架。这样做需要新增不可变制品、
来源合同和发布流程，影响面超出安装完整性修复。当前先采用有限重试、超时、
逐项核验和同版本自愈；镜像方案后续可作为独立供应链任务评估。

## 验证

- Core 单元测试覆盖：成功修复、失败阻断、阶段错误透传、未声明兼容、路径
  越界拒绝和同版本接线顺序。
- Core CLI 端到端测试覆盖：同版本 repair 失败时退出非零，且不得输出
  `up to date`。
- 能力索引测试反转飞书/微信 provider 顺序，货架与本地标题仍逐字一致。
- 最终门禁数字和突变结果在分支交付说明中记录；独立验收、合并、标签和发布
  不在本文结论范围内。
