# WO-088 卡住型自愈可观测性

## 背景

真机用 `SIGSTOP` 冻结运行时后，心跳链能在约两分钟内强制重建会话，但此前没有持久痕迹，四小时一次的控制机巡检看不到短暂自愈；停止态子进程还可能脱离 tmux 后继续占用资源。离线快照同时缺少可用的活动时长与来源。

## 关键决策

- 所有由守护触发的强制会话重建统一经过 HealthEngine 自愈入口，写一行 `SELF-HEAL performed` 本地日志，并把累计次数、最近时间、原因、清理结果和窗口内事件写入 activity-monitor 快照。
- 四小时内达到三次自愈时锁存 `self_heal_attention_required`。四小时与控制机巡检周期一致；三次用于区分一次偶发恢复和持续反复故障。标记保持到后续人工处理，避免巡检错过短窗口。
- 自愈可观测信息只写本地日志与状态快照，不调用客户通知，也不改变 TD-158 “有积压才告警管理员”的合同。
- 清理前先记录 tmux pane 的精确进程树；杀会话后只对这些 PID 依次发 `SIGCONT`、`SIGTERM`，宽限期后对仍存活者发 `SIGKILL`。不使用全局 `pkill`。
- 离线快照优先沿用最后一次真实活动时间与来源；从未取得活动样本时才使用 guardian 的离线时长推导，并明确标为 `guardian_liveness`。

## 未采用

- 不把运维自愈信息发送给客户。客户消息不是运维告警通道。
- 不以“进程还在”替代心跳判活；本次真机故障正是进程和 tmux 都在、运行时却已冻结。
- 不只写日志文件。控制机四小时轮询无法可靠命中约两分钟的恢复窗口。
- 不用进程名或宽泛进程组清理，避免误杀同机无关任务。

## 自动验证

- 真实 tmux 测试启动隔离会话，冻结其子进程，确认清理前为 `T` 状态、清理后会话和子进程均不存在。
- 单元测试覆盖精确树收集、`SIGCONT` / `SIGTERM` / `SIGKILL` 顺序、无关 PID 不受影响及清理结果计数。
- 心跳、粘滞错误、鉴权恢复和冻结探针均经过同一自愈记账入口；测试负向断言客户通知调用数为零。
- 测试覆盖累计计数、最近原因/时间/清理结果、四小时三次升级、重启恢复和离线活动字段。
- Node 24.18.0 / npm 11.16.0 下：Jest 473/473、Node 1608/1608、6 个依赖根 0 漏洞、正式包 494 项，内容摘要 `1f6db7f...73fa7`，两次打包 SHA-256 均为 `bfe8b240...d39ba`，`npm run verify` PASS。
- 五刀反证均报红：移除 `SIGCONT`、把升级阈值改为四次、绕过自愈记账、丢掉离线活动来源、把飞书版本退回已发布版本。恢复后两个仓工作树干净。
- 真机恢复时间、旧运行时 PID 归零和客户侧零打扰仍由小A独立复验，本开发记录不冒充该证据。

## 影响范围

改动仅影响运行时强制重建的进程清理、activity-monitor 本地日志与状态快照。消息入队、TD-158 告警条件、渠道收发、自卸载、发布源和客户可见回复均不改变。
