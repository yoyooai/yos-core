# 货架自动站外备份

## 背景

2026-08-12 首次人工站外备份闭环：生产货架 924 个文件上传 COS、全量回读，
并在另一台机器恢复后通过货架全量校验。人工流程证明了备份协议，但没有解决
“下一次是否有人记得做”。本功能把已验证的上传、校验和恢复工具编排为周期任务。

## 关键决策

- 调度器放在控制机，不放货架机。长期云密钥不进入货架机。
- 每轮凭据限定到唯一 run 前缀、无删除权、短期失效，只在内存和 SSH stdin 中传递。
- 成功条件固定为：前置全量自审、上传、反向校验、后置身份自审、元数据出站并回读；
  首轮及每 N 轮还必须恢复并全量核验。
- 前后两次货架身份必须一致，防止发布切换与自动备份并发后把一棵树的自审和另一棵树
  的文件拼成一份“通过”证据。
- 状态原子写入，活进程锁永不按时间抢占；死进程旧锁超过阈值后才恢复。
- `keepSuccessful` 只生成清理候选。自动备份没有删除 COS 的接口和权限。
- systemd 安装器只接受系统级部署，以指定普通账号运行，保留全部沙箱强度；安装过程真实
  触发一次完整备份，成功后才启用 timer，失败则恢复旧 unit 和 timer 状态。

## 否掉的方案

- **cron**：能定时，但缺少明确的 oneshot 状态、持久补跑、超时与统一日志边界。
- **货架机保存长期密钥**：省掉跨机，但把只读生产机变成可访问整个备份桶的密钥宿主。
- **自动清理旧前缀**：需要给定时任务删除权；一次脚本或凭据事故可能抹掉所有恢复点。
- **只上传不恢复**：只能证明“对象存在”，不能证明货架机全损后另一台机器能用它重建。

## 当前验证

- 小A首次真机验收发现生成的 `WorkingDirectory=` 被整体双引号包裹，systemd 将其判为
  非绝对路径，unit 为 `bad-setting` 且程序内告警没有机会启动。根因是生成器把适用于
  `ExecStart=` 参数的引号规则错误复用于 `WorkingDirectory=`。
- 返修改用 systemd 路径转义，并新增真实 `systemd-analyze verify` 回归；Linux 门禁缺少
  `systemd-analyze` 时直接失败，不再把“只检查文本”冒充为 unit 可运行验证。
- 候选分支返修前全量门禁：Jest 468/468、Node 1544/1544、6 个依赖根 0 漏洞、
  正式包 481 项，双打包字节一致，`npm run verify` PASS。
- 编排与 systemd 生成器定向测试覆盖正常链、失败告警、密钥脱敏、并发锁、旧锁恢复、
  货架切换竞态、恢复身份、保留候选、命令接线、子进程树超时清理和 unit 注入。
- 四道关键防线做过突变验证：拆掉反向校验、货架身份竞态判断、敏感 stderr 抑制、
  `ProtectSystem=strict` 时，对应测试均精确报红；恢复代码后定向测试全绿。
- 真实子进程超时测试证明孙进程不会在调度器退出后继续写磁盘。
- 小A已完成真实 SSH、COS、定时触发、失败告警和异机恢复验证；本次 systemd unit 返修
  仍待增量复验，通过前不合并、不部署。
- 0.1.16 独立复核确认 TD-149 的边界有意保留：JSON 模式只做机械安装，不执行钩子；
  终端模式下加装件失败会明确标为 degraded，但渠道基础能力仍可用，因此整体退出码仍为 0。
- TD-154 返修改为系统级 unit，并新增真实服务触发、告警写目录预检、新装失败清理、覆盖失败
  恢复旧 unit/启用状态的测试。代码仍在隔离分支，未合并、未打标签、未部署；生产当前的
  手工系统级绕法不能替代本分支的小A独立真机复验。
